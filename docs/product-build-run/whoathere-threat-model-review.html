The core WhoaThere direction is right, but the threat model must be framed wider than install scripts.

Recent npm and PyPI incidents show the same pattern repeating: trusted package identities are compromised, release pipelines are abused, registry artifacts differ from source repos, and malicious behavior moves into postinstall hooks, Python startup hooks, native build paths, binary wheels, CLI entrypoints, import-time code, and normal-looking API calls. WhoaThere should be described as package artifact admission control, not just an install-script sandbox.

Fail-closed remains the right default Current catch is mostly prevention-by-denial Allow verdicts are not yet production-proven Binary and API-use behavior must be first-class AWS Vault framing still fits the threat

Bottom Line

What the current build would stop

If developers and CI actually go through WhoaThere shims, the current MVP blocks high-risk npm and pip installs before package-manager execution. That would have prevented many recent compromises from running during install.

What it would not yet prove

It would not yet prove that a specific package version is safe to admit. The production system still needs real Vault fetch, full transitive archive scanning, native/binary analysis, isolated detonation, provenance checks, release diffing, and digest-bound promotion.

Threat-model correction

Malicious install scripts are one execution surface. The better model is: any package artifact may execute during install, build, import, interpreter startup, CLI invocation, native loading, or ordinary API use.

Most important product constraint

Do not convert evidence into broad trust. Verdicts must bind to exact ecosystem, name, version, digest, source metadata, dependency closure, platform, policy, and detonation profile.

Assessment: the plan is not overbuilt for the current threat. The main risk is the opposite: shipping with a narrow "bad postinstall" story while attackers have already moved into trusted release compromise, Python .pth startup hooks, native build files, binary wheels, and API-compatible backdoors.

Incident Patterns

The recent campaigns are not isolated one-off tricks. They expose several durable root causes that should drive the WhoaThere architecture.

Pattern What Happened Recently Architectural Implication
Trusted maintainer or publisher compromise Axios, LiteLLM, Telnyx, Intercom, Mastra, and other incidents involved real package names or trusted publishers, not just obvious typosquats. Name reputation is weak evidence. The Vault must verify the exact release artifact and apply cooldown, publisher-change, and release-pattern checks.
Registry artifact differs from source Several attacks placed malicious code only in npm or PyPI artifacts while GitHub looked clean or lagged behind. WhoaThere must inspect downloaded registry artifacts directly and compare them to source tags, commits, and expected release workflows.
Valid provenance can be malicious Miasma-style cases abused real CI/OIDC paths, producing releases that looked properly published. SLSA/OIDC/Sigstore should be evidence, not an allow decision. Behavior and release anomaly evidence must still pass.
Execution hides outside lifecycle scripts Python .pth files, import-time payloads, npm bin entrypoints, binding.gyp, native extensions, and binary wheels all appeared or are natural attacker moves. The detonation matrix must cover install, build, startup, import, CLI entrypoint, native load, and representative API-call paths.
Second-stage payloads and blob hiding Incidents used Bun downloaders, disguised media files, generated payloads, encrypted JavaScript, and platform-specific binaries. Archive scanning must classify executable blobs, suspicious media, WASM, .node, .so, .dylib, .pyd, .pyz, and bundled executables.
CI and cloud secrets are primary targets Payloads repeatedly hunted GitHub, npm, PyPI, cloud, Kubernetes, Vault, SSH, JFrog, and AI-tool credentials. Detonation environments need fake canaries for these secrets, denied network by default, and explicit evidence for file reads, metadata calls, DNS, and HTTPS egress.
Self-propagating package attacks Several campaigns reused stolen npm or GitHub credentials to publish more malicious versions quickly. Fast cache admission is not enough. Vault needs org-wide quarantine, revocation, retroactive denial, and dependency-closure re-evaluation.

Would WhoaThere Catch It?

"Catch" has two meanings. The current build would often prevent execution by blocking protected installs. It would not yet produce production-grade allow or deny verdicts from real package detonation. The target production design can catch much more, if the recommended gaps below become explicit requirements.

Plan Review

What is strong

  • Fail-closed behavior is correct for unknown high-risk npm and pip execution.
  • Local shims plus Vault steering are the right ergonomic path for developers and CI.
  • AWS Vault remains the strongest deployment fit for isolated detonation, private networking, and content-addressed cache control.
  • The proof-binding model in Phase 2 is directionally right: provider, subject, context, freshness, Vault host, and replay resistance matter.
  • The Phase 4 schema work is valuable because it separates fixture evidence from real production evidence.

What is underframed

  • The phrase "malicious install scripts" is too narrow for the product promise.
  • Binary wheels, native extensions, binding.gyp, Python .pth, interpreter startup, and API-use behavior need first-class status.
  • Transitive dependency closure is a core requirement, not an enhancement.
  • Valid provenance must be treated as a signal to verify, not as permission to run.
  • Developer-tool credentials and AI-tool persistence are now part of the practical blast radius.
Conclusion: do not restart the plan. The architecture is well positioned. Update the framing, promote a few "later" concerns into the MVP security standard, and keep the current sequential phase structure.

Build Review

Based on the current report and checkpoints, the implementation is a useful local security prototype. It is not yet a production admission system.

Area Current State Threat-Model Assessment
Endpoint interception Local CLI/shim behavior exists for supported npm and pip flows, with high-risk execution blocked. Good MVP control, assuming developer and CI adoption are enforced. Not sufficient for already-installed packages or runtime execution.
Isolation proofs Readiness levels and proof binding are modeled, but real macOS/Linux containment is not yet production-verified. Correct to keep high-risk execution fail-closed. Do not allow installs based on beta providers or diagnostics.
Vault proxy Local-dev data-plane and cache/admission routes exist. Real AWS fetch, storage, worker, and network isolation are not deployed. The Vault is the right place to solve package admission. It must own transitive archive closure and digest-bound promotion.
Detection and detonation Static scanning and dynamic behavior evidence are fixture-safe and deterministic. Useful contract work, but not yet evidence that real malware families are caught. Red-team fixtures should now model recent campaigns.
Docs and claims Docs already state local-dev limits and non-production status. Keep that discipline. Add the broader artifact/admission framing so readers do not think scripts are the whole problem.

Where Attackers Go Next

The recent incidents point to predictable evasions. These are not reasons to abandon the design. They are requirements for the next validation loop.

  1. No visible lifecycle scripts. Payloads move to binding.gyp, PEP 517 build backends, .pth, sitecustomize.py, npm bin entrypoints, native extensions, or WASM.
  2. Valid-looking provenance. Attackers compromise the actual workflow or publisher so SLSA/OIDC metadata appears normal.
  3. API-compatible malicious behavior. Packages preserve expected APIs and exfiltrate only on real client construction, request signing, model invocation, upload, or cloud SDK calls.
  4. Platform and environment gating. Code activates only on Linux CI, macOS developers, specific CPU architecture, CI=true, GitHub Actions, AWS/GCP/Azure metadata reachability, or valuable files.
  5. Second-stage trust laundering. Payloads download from GitHub Releases, Hugging Face, package CDNs, cloud storage, or already-installed developer tools rather than obvious throwaway infrastructure.
  6. Delayed updates. A benign package builds reputation, becomes transitive in popular projects, and turns malicious days or weeks later.
  7. Tooling compromise outside package managers. VS Code/OpenVSX extensions, AI coding tool config, CI plugins, pre-commit hooks, and repo-local automation become package-equivalent execution surfaces.

Recommendations

Priority Recommendation Why It Matters Where It Fits
P0 Reframe WhoaThere as package artifact admission control. Install scripts are one surface. Recent attacks prove the unit of trust is the artifact plus behavior, not the script field. Docs, product language, Phase 3/4 goals.
P0 Keep high-risk execution fail-closed until exact containment and Vault-only egress proofs exist. The current MVP's strongest real security property is prevention before execution. Phase 1/2 invariant.
P1 Make full transitive archive closure a Vault admission requirement. Mastra-style attacks hide in transitive packages while first-party code looks clean. Phase 3 cache-miss pipeline.
P1 Add archive classifiers for wheels, sdists, native modules, .pth, binding.gyp, WASM, blobs, executables, and second-stage indicators. Attackers are moving into package shapes that do not look like npm lifecycle scripts. Phase 4 static scanner.
P1 Expand detonation to install, build, interpreter startup, import, CLI entrypoint, native load, and minimal API-call probes. LiteLLM, Hades, codexui-style attacks may not fire during install alone. Phase 4 detonator.
P1 Seed canary credentials for GitHub, npm, PyPI, cloud providers, Kubernetes, Vault, SSH, CI, and AI-tool auth. Recent malware repeatedly hunts these exact files and environment values. Phase 4 behavior analysis.
P1 Treat provenance as evidence, not approval. Miasma-style compromise shows valid provenance can coexist with malicious payloads. Phase 3 policy and Phase 4 admission verdicts.
P1 Add release-diff and source-to-registry comparison. Many poisoned releases had clean GitHub repos but malicious registry artifacts. Vault fetch workers and scanner jobs.
P1 Add cooldown/manual review triggers for new maintainers, dormant packages, changed workflows, new binary files, and high-centrality packages. Fast-moving worm campaigns exploit the short window before humans notice. Policy service and admin workflows.
P2 Track developer-tool artifact classes after package-manager MVP. AI coding tools, VS Code extensions, and repo-local automation are becoming part of the same blast radius. Later expansion, not Phase 1/2.

MVP Standard Update

The MVP does not need to perfectly detect every possible runtime backdoor. It does need to avoid overclaiming and it must cover the most common high-impact execution surfaces seen in current npm and PyPI attacks.

Minimum secure MVP statement: WhoaThere MVP may claim it prevents unapproved high-risk package execution through protected npm and pip workflows. It should not claim that a package is safe unless the exact artifact digest and dependency closure have passed the configured static, provenance, source-diff, and detonation requirements.

Must be in or before production Phase 3/4

  • Digest-bound admission verdicts for npm tarballs, PyPI wheels, and sdists.
  • Full transitive dependency closure for npm and pip lock/index resolution.
  • Registry artifact scanning, not only source repo inspection.
  • Detection for lifecycle hooks, PEP 517 hooks, .pth, native build files, and CLI entrypoints.
  • Isolated behavior probes with denied network and seeded canary secrets.
  • Release-source-provenance diffing with provenance treated as a non-authoritative signal.

Can remain later than MVP

  • General runtime application protection after a package has been admitted.
  • Full semantic API fuzzing for every library surface.
  • Windows endpoint isolation.
  • VS Code/OpenVSX/AI-tool extension admission, as long as package-manager scope is stated clearly.
  • Perfect detection of long-delay, low-probability, or customer-specific API triggers.

Open Questions

  1. Representative API probes: which packages get API-use detonation, and how do we generate safe, meaningful calls without requiring customer source code?
  2. Binary verdict confidence: what is the minimum acceptable evidence for native extensions and binary wheels before an enterprise cache can promote them?
  3. macOS-first endpoint versus Linux-first detonation: macOS matters most for local developers, but Linux is the fastest path to strong, repeatable Vault detonation. The plan should keep both truths explicit.
  4. Break-glass policy: what is the acceptable workflow when a critical build is blocked by quarantine, especially for CI fail-closed customers?
  5. Retroactive revocation: how quickly should Vault invalidate and re-scan cached packages when new intelligence arrives?
