## Outcome

The first drop-accounting gate now creates a real, bounded sensor gap rather than accepting a
synthetic counter or corpus label. A root-owned raw-syscall BPF program filters to the exact
fault-injector process and its `getpid` trigger, then reserves an eight-byte record in a protected
4 KiB ring buffer. The host does
not consume that buffer. The probe makes exactly 2,048 trigger syscalls, detaches the program, and
reads an independent protected array-map counter that the BPF failure branch increments atomically
whenever `bpf_ringbuf_reserve` returns `NULL`.

On the final physical run, the kernel accepted 255 reservations and rejected 1,793. Strict Swift
and Rust decoders require both values to be positive and require `255 + 1,793 = 2,048`; a zero,
relabeled, duplicated, noncanonical, or arithmetically inconsistent record fails closed. The guest
receipt binds the positive dropped-event count and reports `incomplete_on_injected_gap`. The host
independently reports a healthy packet sensor, zero dropped frames, zero raw frames, terminated
guest channel, stopped VM, and destroyed diskless execution instance with the same terminal.

The first diagnostic boot produced the correct protected drop evidence but exposed that the Swift
final-case verifier still required `observation_complete` for every case. It denied the receipt and
issued no authority. For injected gaps, the verifier now mirrors the existing strict Rust terminal
policy: only the two guest-drop cases may satisfy this terminal with a positive guest drop count and
zero host drops; `host_frame_overflow` requires the inverse; all unrelated labels fail. A focused mutation
test covers zero-drop and terminal-substitution attempts before the successful rerun.
