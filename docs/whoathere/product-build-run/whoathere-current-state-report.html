WhoaThere is a strong local-dev security prototype, not yet a deployable 1.0 system.

The project now has a working Rust workspace with local CLI interception, policy/source checks, fail-closed launch planning, provider diagnostics, a bounded local Vault data-plane simulator, promoted-cache registry routes, static scanning, fixture-safe dynamic behavior evidence, and audit-safe admin workflow contracts. The major security shape is right: unknown or unproven package execution does not proceed. The missing work is the hard production boundary: real macOS VM isolation that can run npm/pip/uv safely, real install/detonation telemetry, safe sync-back, and later the AWS Vault persistence and fetch workers needed for enterprise use.

Fast Take

What works today

WhoaThere can wrap supported npm and pip entry points, inspect package sources and config, deny high-risk installs before execution, produce redacted audit records, and exercise Vault/cache/admission behavior locally.

The threat is broader than scripts

The product must also handle binary wheels, native extensions, import-time payloads, and packages that keep the expected API shape while adding malicious behavior when that API is used.

What is intentionally blocked

Real package installs, lifecycle scripts, Python build backends, imports, public registry fetches, scanner workers, and dynamic malware execution are not allowed by the current MVP.

Why that is good

The current system does not pretend configuration steering is a sandbox. It fails closed until a future provider proves containment and Vault-only egress for the exact launch.

Plain-English status: this is useful as a security-shaped prototype and local validation harness. It is not yet a tool you would deploy to developers and allow to run untrusted package code, binary artifacts, or API-level behavior probes.

Mental Model

WhoaThere is trying to stop malicious npm and pip packages from reaching secrets, networks, and build systems during install, build, import-time, and admission-time behavior checks. That includes classic lifecycle scripts, Python build backends, binary wheels, native extensions, and packages that look API-compatible but add malicious side effects when their normal functions are used. It does that in two layers: a local endpoint engine and a private Vault proxy.

1. Developer or CI runs npm/pip PATH shims and command classification decide whether this is a protected workflow.
2. Local engine checks policy Source files, lockfiles, requirements, package identity, and registry/index settings are inspected.
3. Execution is blocked unless proven safe High-risk install/build/import execution requires verified containment and Vault-only egress.
4. Vault admits package artifacts Local simulation models quarantine, evidence, digest-bound cache promotion, and promoted-only serving.
5. Evidence drives allow/deny/review Static and fixture-safe dynamic evidence can be bound to exact artifact, job, tenant, and audit context.

The key design rule is simple: do not execute or serve a package just because it looks configured correctly. A package is allowed only when the right evidence exists and is bound to the exact package digest, request, policy, and execution context. Full application runtime protection is still out of scope, but package admission needs enough install, build, import, and representative API-use probes to catch malicious behavior before approval.

Security Model: Current

The current system is a fail-closed local security prototype. Its strongest property is that supported high-risk npm and pip workflows are stopped before package-manager execution unless the exact proof requirements are satisfied. It is useful as a guardrail and validation harness, but it is not yet a production sandbox or production package admission service.

Security Model: Target

The target system is a digest-bound admission-control platform. Package managers should receive only artifacts that Vault has fetched into quarantine, verified, scanned, detonated where required, and promoted into a servable generation. Endpoint enforcement, Vault serving, scanner evidence, detonation evidence, policy, and audit all bind to the same artifact digest and policy context.

It still does not claim universal runtime protection after an admitted package is used in arbitrary application code.

Security Model: Gap Filling Plan

The gap is not conceptual; the contracts are mostly in place. The remaining work is to turn the modeled boundaries into production controls, then keep the launch claim narrow until each artifact class has evidence that justifies promotion.

  1. Lock the security claim. State that v1 prevents unapproved high-risk npm/pip execution and serves only digest-approved Vault artifacts. Do not claim universal malware detection, production macOS sandboxing, or runtime app protection.
  2. Define v1 artifact classes. Auto-allow only npm.registry_tarball.v1 and pypi.pure_wheel.v1 after complete evidence. Route native, binary, direct, VCS, editable, unknown, and unsupported platform-selector classes to manual review or deny.
  3. Build durable Vault state. Move admission, metadata, evidence, verdict, alias, audit, review, and break-glass state from local-dev simulation to AWS-backed storage and transactions.
  4. Implement atomic promotion. Advance servable_generation only when CAS object, metadata snapshot, source policy, evidence profile, verdict, and alias update match in one transaction.
  5. Resolve and scan full dependency closures. Fetch, hash, unpack, classify, and scan the full npm/PyPI closure before serving any newly requested artifact.
  6. Add scanner coverage for modern attack surfaces. Cover lifecycle scripts, PEP 517, .pth, sitecustomize.py, npm bin, binding.gyp, native files, wheels, WASM, executable blobs, suspicious URLs, credential path strings, and registry-vs-source drift.
  7. Prove Linux detonation. Run non-destructive malware fixtures inside isolated Linux workers with no host secrets, no IMDS, bounded resources, fake canary secrets, denied/recorded egress, and redacted evidence output.
  8. Make macOS honest and useful. Keep macOS first for endpoint UX, source policy, audit, Vault routing, and fail-closed protection, while labeling local containment as beta until production isolation is proven.
  9. Ship the minimum control plane. Provide policy CRUD/validation, manual review, break-glass lifecycle, audit search/export, privacy export/delete, revocation, rollback, and incident notification before enterprise rollout.
  10. Gate release with adversarial tests. Require no public fallback, no unapproved serving, no broad break-glass, outage fail-closed behavior, redacted evidence, dependency-confusion denial, warm-cache scale, and mock-malware fixture coverage.

Gap-plan rule: do not broaden auto-allow coverage because a scanner is promising. Broaden it only after that artifact class has complete evidence profiles, production detonation, outage tests, privacy tests, compatibility tests, and rollback behavior.

Admission signals to add

  • Known-good package diffs: when Vault has a previously approved version or digest, compare the new artifact against that known-good baseline. Diff registry artifacts directly, not only source repositories, and flag new lifecycle hooks, build hooks, .pth files, native files, dependency changes, obfuscated code, and suspicious credential or network references.
  • AI-assisted review as triage: use AI and static code scanning to summarize risky diffs and generate reviewer notes, but never let an AI summary create an allow verdict by itself.
  • Package reputation: score downloads, repository age, GitHub stars, maintainer history, release cadence, issue activity, recent ownership changes, provenance changes, and ecosystem centrality. Reputation should reduce review friction for boring changes, not override missing evidence.
  • External tool integrations: evaluate public repo-quality and supply-chain tools for additional evidence, including vulnerability databases, malware feeds, OpenSSF-style scorecards, secret scanners, dependency analyzers, provenance validators, license scanners, and repository hygiene checks. Integrations should feed reason codes and evidence summaries into WhoaThere, while WhoaThere remains the authoritative policy and promotion decision point.
  • Fresh-release cooldown: by default, do not auto-use packages or versions newer than a configurable age threshold. New packages, first releases after dormancy, and sudden patch bursts should remain quarantined or manual-review until policy, evidence, and age gates pass.
  • Unpinned dependency stabilization: when WhoaThere is resolving on behalf of tools like uv, pip, or a requirements.txt file and the requested version is unpinned, prefer the latest approved last-known-good version by default instead of floating to a newer public release. Emit a clear warning and audit event that records the requested range, selected digest, policy reason, and how to opt into reviewing a newer version.

Icebox idea: distributed package attestations

A later version could let end users publish signed "I think this package is evil" or "this package behaved suspiciously" attestations to a shared network. Those reports could become another reputation and review signal across WhoaThere deployments, especially for fast-moving attacks discovered by one customer before others encounter the same digest.

This is intentionally not v1. A shared attestation network would need abuse resistance before it could influence policy: signer reputation, tenant-scoped trust, rate limits, evidence requirements, digest-bound claims, Sybil resistance, appeal/retraction flows, and possibly consensus or zero-knowledge techniques to reduce denial-of-service mischief and protect sensitive reporter context. Until that is researched, external community reports should be treated as manual-review triggers, not automatic denies.

What Is Marginal Or Easy To Misread

These are the areas most likely to be overestimated by a new reader. The code is doing useful work, but the product should not claim more than this.

macOS isolation is not production containment

macOS support is currently readiness detection and beta positioning. It checks for relevant primitives and describes the VM-first path, but it does not run package installs inside a production macOS VM helper.

Linux active probes do not authorize installs

Linux diagnostics and Docker probe paths produce receipts and prove contract boundaries. They still report no proof minting and no execution authorization.

Registry steering is not security

The CLI can point npm/pip configuration at a Vault origin, but the docs and launch code correctly treat this as compatibility setup. Real egress enforcement still needs a provider.

Vault is local-dev shaped

The Vault data plane has strong local invariants, but durable storage, real cloud identity, public upstream fetch, scanner queues, and AWS service deployment are not implemented.

Dynamic behavior is fixture-safe

Phase 4 deliberately uses deterministic mock-canary fixtures. That proves schemas, binding, sanitization, and fail-closed behavior. It does not prove real malware behavior will be observed under production isolation.

Compatibility is not broad yet

The plans call for workspaces, native modules, Python sdists/wheels, markers, extras, subprocess inheritance, cleanup crash cases, and package-manager edge cases. Only a safe subset is implemented today.

API-shaped malicious behavior is not yet proven

A package can keep the same public API and still add hostile side effects inside ordinary calls. The current fixture layer names import-time and native risks, but it does not yet run representative API-use probes for real packages under isolation.

Binary wheels need their own evidence path

Python wheels and native npm modules may contain compiled code that bypasses simple script scanning. Current evidence profiles recognize wheel/native-extension classes, but real binary inspection and isolated install/import/use behavior are still future work.

macOS Local Release Target

The immediate release target is local-first and Apple Silicon only. It comes before the broader enterprise Vault plan: prove that WhoaThere can protect a developer Mac with a real VM boundary, useful npm/PyPI/uv coverage, and honest fail-closed behavior.

Current implementation progress: the CLI now has macOS VM lifecycle/status surfaces, a separate Swift helper that imports Apple Virtualization.framework, uv workflow classification, release-policy commands, canary inventory, sync-policy reporting, and doctor JSON readiness. The helper can report host/framework readiness and initialize a managed disk-import bundle from an explicit local disk image. That disk import is deliberately not lifecycle-ready without auxiliary storage, hardware model, machine identifier metadata, and real signature verification. The helper also has a local IPSW restore-image path that can create raw disk, auxiliary storage, hardware model, and machine identifier metadata when run as an entitled Apple Virtualization helper. A persistent runtime scaffold can start the VM and write host-runtime health proof. The helper now also exposes a vsock guest-readiness challenge and a tiny guest-agent source artifact; vm health still fails closed until that guest proof is produced for the current runtime session. Detonation, egress recording, and sync-back remain deliberately blocked until guest provisioning, signature verification, and runtime control pieces are implemented.

Release claim

WhoaThere runs supported npm, pip, and uv installs inside a macOS guest VM, injects only fake canary secrets, records filesystem/process/package-manager/network behavior, and syncs back only approved project outputs. The release does not claim universal malware detection, safe arbitrary native execution, runtime application protection, or enterprise package admission.

Implemented command contract

  • whoathere vm status --helper <path> reports Rust-side and Swift-helper VM readiness, including precise missing bundle and metadata reason codes.
  • whoathere vm init --execute --helper <path> --image <path> imports an explicit local disk image into the managed bundle and writes config plus manifest metadata, but does not make the bundle bootable or ready.
  • whoathere vm init --execute --helper <path> --restore-image <path> uses Apple Virtualization.framework restore-image APIs to install from a local IPSW and persist required VM metadata, subject to entitlement and host support.
  • whoathere vm init --execute without a helper or image fails closed with exact required inputs rather than creating placeholder readiness.
  • whoathere vm start, suspend, reset, and prune delegate to the helper when configured; start requires bootable metadata and writes host-runtime health proof, while vm health requires a matching guest vsock proof.
  • whoathere vm health --helper <path> is read-only, delegates to helper health, and preserves fail-closed exit code 20 until guest proof is present.
  • The helper includes a whoathere.guest_ready.v1 vsock protocol and guest-agent source under guest-agent/; the agent must be built and run inside the guest before guest health is proven.
  • The helper includes a com.apple.security.virtualization entitlement plist and local signing script for development validation.
  • The Rust CLI invokes the helper with an absolute canonical path, cleared environment, minimal PATH, bounded output, and operation timeouts.
  • whoathere vm release-plan classifies artifact risk and returns model verdict exit codes, but explicitly does not authorize runtime execution or sync-back.
  • whoathere vm canaries lists fake credential classes for npm, PyPI, GitHub, SSH, cloud, Kubernetes, Vault, env files, and AI-tool auth.
  • whoathere vm sync-policy documents deny-by-default sync-back rules, evidence requirements, and external scanner adapters.
  • whoathere doctor --json --helper <path> reports VM readiness, helper availability, and scanner adapter availability without authorizing high-risk execution.

Helper bundle layout

The helper uses a managed state directory with bundle/config.json, bundle/image.manifest, bundle/disk.img, bundle/auxiliary-storage, bundle/hardware-model.bin, bundle/machine-identifier.bin, bundle/runtime.json, bundle/health.json, bundle/guest-health.json, bundle/runtime.pid, bundle/saved-state.bin, logs/, runs/, cache/, reports/, and overlays/.

Admission posture

  • Auto-sync is possible only for npm.registry_tarball.v1 and pypi.pure_wheel.v1 after complete clean evidence.
  • PEP 517 sdists, binary wheels, native extensions, and platform-specific native artifacts require manual review.
  • Direct URL, VCS, editable, local path, unknown, and unsupported package classes are denied by default.
  • Recorded egress is allowed inside the VM for compatibility, but suspicious destinations, DNS tunneling, canary access, or unexpected second-stage downloads block sync.
  • Sync-back is deny-by-default and limited to project dependency outputs such as node_modules/**, lockfiles, project .venv/**, and uv outputs.

Recommended Next Steps

The next work should avoid boiling the ocean. Execute the macOS local release path first, prove the VM boundary, then return to the enterprise Vault plan.

  1. Keep the next release target fixed. Apple Silicon macOS only, CLI only, local-first, npm/pip/uv, VM-backed detonation, recorded egress, and deny-by-default sync-back.
  2. Build the macOS VM helper before broadening scope. The release is not useful until a signed helper can create, start, command, suspend, and reset the macOS guest reliably.
  3. Connect guest execution to launch decisions. The CLI must route supported high-risk npm/pip/uv installs into the guest and keep unsupported global/system installs blocked.
  4. Make sync-back the hard safety gate. Approve only whitelisted project outputs after clean evidence. Native, binary, direct, VCS, editable, suspicious, and unsupported classes stay manual-review or deny.
  5. Run non-destructive red-team fixtures in the guest. Use fake canaries to prove install-script exfil, PEP 517 abuse, import-time payloads, DNS/HTTPS exfil, delayed CI activation, and API-compatible credential theft are detected or blocked.
  6. Compare against open-source tools without overclaiming. GuardDog, OpenSSF Package Analysis, OSV-Scanner, pip-audit, Scorecard, Syft, Grype, and Trivy are evidence sources and comparator gates, not the security boundary.
  7. Run a release-gate audit before enterprise work resumes. Verify the CLI is signed/notarized, VM image manifests are signed, unsupported cases fail closed, docs are honest, and no workflow depends on host secrets or public fallback.

Best-In-Class Offering Plan

This is the later enterprise path after the Apple Silicon macOS local release is proven. The strongest long-term path is to make WhoaThere an AWS-backed package artifact admission system for npm and PyPI, not merely an install-script blocker. The enterprise claim should be precise: WhoaThere prevents unapproved high-risk package artifacts from executing through protected npm/pip workflows and serves only digest-approved artifacts through Vault.

Use the existing Rust workspace and Phase 1/2 endpoint work as the base. Do not restart or redesign. This plan resumes after the macOS VM-backed local release. Its target is AWS Vault GA for CI/private registry serving, with macOS first-class for endpoint UX, policy, audit, and fail-closed protection.

Key changes

  • Reframe docs, gates, and product language around digest-bound package artifact admission control.
  • Split acceptance criteria into v1_release_gate, v1_beta_gate, and post_v1.
  • Auto-allow in v1 only for npm.registry_tarball.v1 and pypi.pure_wheel.v1 after complete evidence.
  • Make native, binary, direct, VCS, editable, unknown, and unsupported platform-selector classes manual-review or deny by default.
  • Treat provenance, OIDC, SLSA, signatures, maintainer reputation, and source repo history as evidence only, never as standalone approval.
  • Bind every allow verdict to ecosystem, package, version, digest, source, dependency closure, platform, package-manager mode, policy version, evidence profile, scanner/detonator versions, Vault host, and expiry.

  2. Production Vault spine: replace local-dev/in-memory Vault state with AWS-backed Rust services using Aurora/Postgres, S3 CAS, SQS, KMS, CloudWatch/Otel, NLB/PrivateLink, VPC endpoints, NAT, and AWS Network Firewall.

  4. Cold-miss pipeline: fetch the full resolved dependency closure into quarantine, hash, unpack, classify, compare source to registry, run provenance/reputation checks, static scanners, and required detonation jobs before any promotion.
  5. Static scanning: classify lifecycle scripts, PEP 517 backends, .pth, sitecustomize.py, npm bin, binding.gyp, native files, WASM, executables, suspicious blobs, credential path strings, second-stage URLs, and registry-only payloads.
  6. Linux detonation: build whoathere-detonator-worker on hardened EC2 workers using per-job namespace/seccomp/cgroup v2/Landlock containment, read-only rootfs, fake home, cleared env, bounded resources, no IMDS, and Vault-only evidence egress.
  7. Behavior probes: run npm lifecycle/install smoke, require/ESM import smoke, declared bin --help/--version, PyPI wheel install, interpreter startup for .pth, top-level import smoke, and limited API-use canary probes.
  8. Control plane: ship minimal policy CRUD/validation, namespace/source rules, manual review, break-glass lifecycle, evidence summaries, audit search/export, privacy export/delete, admin identity, and incident notification. Dashboard polish is not required for v1.

Interfaces

  • CLI additions: whoathere vault login, whoathere policy sync, whoathere cache prewarm, and whoathere explain <audit_event_id>.
  • Vault APIs: health/readiness, npm facade, PyPI Simple facade, admission request/status, verdict lookup, artifact serving by digest, evidence profile listing, policy/source rules, manual review, break-glass, audit export, and privacy export/delete.
  • Core types: ArtifactClass, ClosureManifest, EvidenceProfile, EvidenceJobKind, DetonationJob, BehaviorEvidence, ReleaseDiffEvidence, ProvenanceEvidence, ServableGeneration, SourcePolicy, and RedactedEvidenceSummary.
  • API errors: every non-2xx response includes reason_code, retryable, audit_event_id, policy_version, and admission_request_id.
  • Registry invariant: protected npm/PyPI metadata must never point clients at public upstream artifact URLs.

Test plan

  • Final validation: Rust tests, clippy with -D warnings, fmt check, OpenAPI/schema tests, and Terraform validate/plan in AWS staging.
  • Invariant tests: no public fallback, no unapproved bytes served, no allow without complete evidence, no stale or partial promotion, no tenant mismatch serving, and no break-glass durable allow.
  • Red-team fixtures: npm postinstall exfil, npm prepare fetch, binding.gyp, npm CLI-bin token theft, API-compatible constructor exfil, PEP 517 backend abuse, wheel .pth, import-time payload, native marker, DNS/DoH/HTTPS exfil, platform split, delayed CI=true, dependency confusion, maintainer takeover diff, and valid-looking provenance.
  • Performance gates: 1,000 concurrent warm CI jobs, large artifact streaming without full buffering, metadata fanout, cold-miss admission timing, and scanner/detonator backlog behavior.
  • Operations gates: Vault outage, scanner outage, detonator outage, CAS tamper, policy outage, audit outage, rollback, revocation, break-glass expiry, and incident drill.

Assumptions and boundaries

  • AWS-only dedicated enterprise deployment is the v1 default; Cloudflare remains later.
  • Rust remains the implementation language, and npm/PyPI are the only v1 ecosystems.
  • macOS is the first endpoint UX priority; Linux is the first production containment and detonation proof path.
  • Best-in-class means strong boundaries, accurate claims, high-quality evidence, reliable fail-closed behavior, and excellent operational recovery, not universal malware certainty.
  • Windows, Cloudflare deployment, full runtime app protection, broad IDE/plugin scanning, TLS MITM, raw payload capture, customer source-code collection, and full environment dumps are not v1 goals.
