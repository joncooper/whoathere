The current WhoaThere build helps you try risky package installs inside a VM first.

It is designed to make supported npm, pip, and uv installs safer by running risky install and build behavior inside a separate macOS virtual machine. Your real Mac's secrets are not copied into that VM. WhoaThere records what happened and copies files back to your project only when the run looks clean and the files are on a short list of expected outputs.

Tested on Apple Silicon Signed and notarized release file tested Local-first CLI Does not auto-trust public packages Does not protect apps after install

The Problem It Addresses

npm, pip, and uv sometimes run code from a package while installing it. In npm this can happen through install scripts such as postinstall and prepare. In Python this can happen through setup.py, modern build hooks, import-time code, .pth startup files, native extensions, and binary wheels. Without extra protection, that code runs on your developer machine with access to environment variables, dotfiles, package-manager tokens, SSH keys, cloud credentials, project secrets, and the network.

WhoaThere changes that default. Instead of running package-controlled code directly on your Mac, the current macOS beta checks the requested install, runs supported risky parts in a VM, reviews the recorded results, and only then decides whether files should be copied back to your project.

How The Current Version Works

The current release path is Apple Silicon macOS only. The main pieces are a Rust command line tool, a Swift helper that starts and talks to the macOS VM, a small program inside the VM that runs package-manager commands, and repeatable test scripts for the release.

1. Check The Request WhoaThere inspects the requested npm, pip, or uv command and rejects unsupported or unsafe forms before the package manager runs.
2. Copy A Safe Project View It builds a temporary copy of the project without your secrets, credential files, symlink escapes, path escapes, risky binaries, or unsupported dependency forms.
3. Run It In The VM The install, build, import, or command check runs inside the macOS VM with fake test credentials instead of your real secrets.
4. Copy Back Or Block Clean recorded results can allow a narrow file copy back. Suspicious behavior, unsafe package types, stale checks, or missing checks cause WhoaThere to block.

What The VM Gets

  • A cleaned-up copy of the relevant project files.
  • The npm, pip, Python, or uv tools needed for the checked command.
  • Fake test credentials in places where stolen secrets often live.
  • No real home directory, SSH keys, npm/PyPI tokens, cloud credentials, Kubernetes config, or project .env secrets from your Mac.

What Comes Back

  • A structured summary: allowed or blocked, reasons, fake-secret access, file activity, tool readiness, command type, and sanitized status.
  • Optional file copy-back only for clean runs and only for approved output paths.
  • No raw fake-secret values, raw real secrets, or raw package-manager output in the structured summary.

How This Improves Security

Blast radius is smaller

Malicious install or build code runs in the VM instead of your normal shell. The VM does not receive your normal developer secrets.

Secret theft becomes visible

The VM gets fake tokens and credential files. If a package tries to read them or send them out, WhoaThere records that and blocks file copy-back.

Copy-back is strict

Your Mac does not blindly copy VM output back. Path escapes, symlinks, native or binary outputs, fake-secret paths, and unsupported locations are rejected.

Risky package types are blocked

Native extensions, binary wheels, VCS dependencies, direct URLs, editable installs, and unknown package types are not automatically trusted in the current beta.

Readiness is checkable

whoathere doctor --json reports whether the VM setup, release checks, copy-back checks, notarization, and VM start/stop checks are current.

Claims are intentionally narrow

WhoaThere does not say "a scanner passed, so this is safe." It requires the VM run, recorded results, and copy-back rules to line up.

Security improvement: for supported local macOS commands, using WhoaThere is meaningfully safer than running raw npm, pip, or uv directly on your Mac because untrusted package-controlled code does not get normal access to your secrets and files.

What It Can Do Today

Current strengths

  • Run supported install, build, import, and command checks inside a macOS VM.
  • Keep your Mac's secrets out of the VM project copy.
  • Use fake secrets to detect credential access and attempts to send credentials out.
  • Detect or block malicious npm install-script test cases.
  • Detect or block Python setup.py, modern build-hook, import-time, and .pth startup-file abuse test cases.
  • Block rather than guess when required setup checks, release checks, notarization, or copy-back proof files are missing or stale.
  • Prevent unsafe VM output from being copied back to your Mac.
  • Give a machine-readable readiness view through doctor --json.

Current hard boundaries

  • No universal malware detection claim.
  • No broad protection after your application imports and uses a package later.
  • No automatic trust for arbitrary public packages.
  • No automatic trust for binary wheels or native extensions.
  • No team-wide server, shared cache, central policy, central audit log, or team override process yet.
  • No Windows support and no current Linux release claim.
  • No complete DNS/HTTPS network monitor yet; current network checks are strong for the test cases but not complete monitoring.
  • No guarantee that API-compatible malicious behavior will be triggered unless probes or tests exercise it.

What This Means In Practice

WhoaThere is best understood as a safer way to try a package install before giving it access to your real workstation. It is not a magic proof that a dependency is harmless forever.

If a package is malicious during install

This is the current beta's strongest case. Install scripts, build hooks, setup hooks, import-time behavior, and fake-secret theft attempts are pushed into the VM and can block file copy-back.

If a package is malicious only when used later

WhoaThere can help only if its checks or your project tests exercise that path inside the VM. Broad protection after the package is installed and used by an app remains future work.

If a package contains native or binary code

The current safe behavior is to deny or require manual review. That is the right security choice for the beta, but it means some legitimate packages will be blocked.

If a package comes from a public registry

The current local-only release does not claim it can safely accept arbitrary public packages. That belongs in the next layer: package reputation, history of known-good versions, scanner integrations, and eventually a shared package cache.

Expected friction: a security-useful beta should sometimes say no. Blocking native, binary, direct, VCS, editable, unknown, or public registry cases is not a bug in the current release. It is how the tool avoids claiming safety before it has enough proof to allow those cases.

Scanner Signals

WhoaThere now has a scanner layer for extra checks. It can use tools such as GuardDog, OSV-Scanner, pip-audit, Syft, and Grype to look for suspicious package behavior, known vulnerabilities, and package contents. Trivy and Scorecard are detected and reported for follow-up use.

These scanner results are useful, but they are not proof that a package is safe. A clean scanner result does not let a package skip the VM, does not allow unsafe files to copy back to your Mac, and does not make binary or native packages automatically trusted.

What scanners add

They can catch known bad patterns, known vulnerable versions, suspicious metadata, and unexpected package contents before a developer trusts a package.

What scanners do not add

They do not replace VM isolation, fake-secret checks, strict file copy-back rules, or manual review for risky package types.

What To Check Before Using It

Before treating the local beta as ready, ask the tool for its current status instead of relying on memory of an earlier test run.

  • whoathere doctor --json should report release_ready: true.
  • release_blocking_reason_codes should be empty, meaning the tool sees no current release blockers.
  • The VM setup should be current and tied to the helper code that will run commands inside the VM.
  • Release test, file-copy test, VM shutdown, and Apple notarization proof files should be present and current.
  • high_risk_allowed should remain false for this beta.
  • Unsupported commands should block instead of quietly running npm, pip, or uv directly on your Mac.
Do not bypass the gate: if the VM is stale, VM setup is stale, a proof file is missing, or doctor reports blockers, the safe answer is to rerun setup or validation. WhoaThere should not silently run the package manager directly on your Mac.

What Comes Next

The next work should expand what WhoaThere can safely handle without weakening the core rule: try risky package behavior somewhere isolated first, then copy back only what is safe. The highest-value additions are:

  • Install testing on another Mac, or in the cleanest available VM-like environment, for more release confidence.
  • Deeper scanner pressure testing with real public packages and stronger repository reputation signals.
  • Known-good package history and diffs against the last approved version.
  • Fresh-release cooldowns and package reputation scoring for public packages.
  • VM runs that execute project tests or generated package-use checks to catch packages that are malicious only when their APIs are used.
  • A team server: shared package cache, central rules, audit log, review flow, and no silent fallback to public registries.
